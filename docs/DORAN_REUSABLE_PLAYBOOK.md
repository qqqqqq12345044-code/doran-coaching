# 재사용 가능한 웹 프로젝트 플레이북

이 문서는 DORAN 프로젝트 고유 정보(브랜드명, 카피, 실제 후기, 실제 지역/키워드 목록 등)를
담지 않는다. DORAN을 만들고 운영하면서 실제로 겪은 설계 결정과 실패 사례를
**다음 웹사이트에도 그대로 적용 가능한 일반 원칙**으로 정리한 것이다. 브랜드 고유
콘텐츠는 전부 일반화했고, 구체적 수치(예: "지역 6,527개")가 필요한 경우는
"프로젝트마다 다른 실제 데이터"라는 전제로만 예시로 남겼다.

---

## 1. 프로젝트 초기 설계 순서

1. **서비스 사실 정리부터**: 실제 존재하는 정보(가격/후기/강사/시험 정보 등)와
   아직 없는 정보를 먼저 명확히 구분한다. 없는 정보는 절대 만들어 채우지 않는다 —
   "나중에 채우면 되지"라는 생각으로 가짜 데이터를 넣으면 실제 서비스와 사이트가
   어긋난 채로 배포되는 사고로 이어진다.
2. **Source of Truth 파일부터 설계**: 브랜드 문구, 서비스 목록, 후기, FAQ 등을
   컴포넌트에 하드코딩하지 말고 `data/*.ts` 형태로 먼저 분리한다. 나중에 분리하려면
   이미 퍼진 하드코딩을 전부 찾아 고쳐야 해서 비용이 훨씬 크다.
3. **라우트 구조를 데이터 규모보다 먼저 확정**: "언어 3 × 목적 4" 같은 조합형
   구조라면, 실제 콘텐츠를 다 채우기 전에 라우트/화이트리스트/네비게이션 구조부터
   설계하고 1~2개 조합으로 끝까지(메타데이터~JSON-LD~반응형까지) 검증한다.
4. **기술 SEO(robots/sitemap/canonical/schema)는 콘텐츠가 적을 때 먼저 세팅**한다.
   나중에 페이지 수천~수만 개가 쌓인 뒤 처음 SEO 구조를 잡으면 마이그레이션
   리스크(URL 변경, 중복 canonical 등)가 커진다.
5. **상담/문의/결제처럼 외부 연동이 필요한 핵심 전환 지점은 가장 먼저 실제
   연동까지 끝낸다.** 디자인은 나중에 다듬어도 되지만, 리드가 실제로 어디론가
   전달되는지는 초기에 실제 테스트로 확인해야 한다.

## 2. Next.js App Router 구성 원칙

- **Server Component 기본, Client Component는 상호작용이 실제로 필요한 leaf에만.**
  폼 제출, 애니메이션 트리거, 로컬 상태가 필요한 컴포넌트만 `"use client"`를 붙이고,
  그 상위 레이아웃/페이지는 서버 컴포넌트로 유지한다. Client Component를 페이지
  최상단에 두면 그 하위 트리 전체가 강제로 클라이언트 번들에 포함된다.
- **데이터와 렌더링을 분리**: 페이지 파일(`page.tsx`)은 "데이터를 어디서 가져와
  어떤 컴포넌트에 넘길지"만 담당하고, 실제 문구 조합 로직은 `lib/`의 순수 함수로
  뺀다. 이렇게 하면 그 로직을 별도 스크립트(`node script.mts`)로 검증하거나
  미리보기(preview) 도구로 확인하기 쉬워진다.
- **동적 세그먼트와 정적 세그먼트의 공존 규칙을 이해하고 설계**: 같은 디렉토리
  아래 고정 경로(`/local/region-search`)와 동적 세그먼트(`/local/[sido]`)가 있으면
  Next.js는 고정 경로를 항상 먼저 매칭한다 — 이를 이용해 "브라우징 허브"와
  "경량 API"를 같은 부모 경로 아래 충돌 없이 공존시킬 수 있다.
- **`generateStaticParams`와 `dynamicParams`는 "빌드 최적화"와 "공개 여부 통제"를
  분리하는 도구로 쓴다.** `generateStaticParams`는 빌드 시점에 무엇을 미리
  만들어둘지(대표 샘플만)만 결정하고, 실제로 어떤 조합을 공개할지는 렌더링 함수
  내부에서 별도의 whitelist 검사로 통제한다. `dynamicParams = true`를 켠다고
  "아무 URL이나 렌더링되는" 구조가 되지 않도록, 반드시 whitelist 검사 +
  `notFound()`를 그 안쪽에 둔다.
- **`layout.tsx` vs `template.tsx` 차이를 명확히 인지**: 라우트 전환 애니메이션처럼
  "페이지가 바뀔 때마다 매번 재실행되어야 하는" 로직은 `layout.tsx`가 아니라
  `template.tsx`에 둔다. `layout.tsx`는 세그먼트 간 이동 시 리마운트되지 않는다.

## 3. SEO 기본 세팅 (metadata / canonical / schema)

- **canonical 도메인은 절대 URL 상수 하나로 고정**하고 env 변수에 의존하지 않는다.
  env 값이 비어있거나 preview 배포 URL(예: `*.vercel.app`)이 들어가면 canonical이
  오염된다 — `SITE_URL = "https://실제도메인"`처럼 코드에 명시 상수로 박아두고
  모든 곳(schema, sitemap, canonical)에서 이 상수 하나만 공유한다.
- **JSON-LD는 "화면에 실제로 보이는 내용만" 변환하는 Builder 함수로 만든다.**
  Breadcrumb/FAQ 등은 화면 렌더링에 쓰는 배열을 그대로 schema 함수에 넘겨서,
  화면과 구조화 데이터가 항상 일치하도록 강제한다. 화면에 없는 임의의
  AggregateRating/Offer/가격을 스키마에만 추가하는 것은 검색엔진 가이드라인
  위반이자 실제 서비스와 어긋나는 정보이므로 절대 하지 않는다.
- **Course/Product류 schema는 실제 값이 있는 필드만 채운다.** 가격/기간/수료증처럼
  아직 확정되지 않은 값은 아예 필드 자체를 넣지 않는다(빈 문자열/추정값 금지).
- **h1은 페이지당 1개, keyword stuffing 금지** — 사람이 읽기 좋은 문장을
  우선하고, 그 문장 안에 자연스럽게 핵심 키워드가 들어가도록 만든다.

## 4. Sitemap Shard 설계

- 페이지 수가 sitemap 프로토콜의 파일당 권장 한도(URL 5만 개 / 50MB)를 넘을
  것으로 예상되면, 처음부터 `generateSitemaps()`(또는 동등한 인덱스 기능)로
  **shard 분할을 전제로 설계**한다.
- **shard 0(또는 별도 index)은 "정적 상위 페이지" 전용으로 가볍게 유지**하고,
  대량 생성되는 콘텐츠(수만~수십만 개)는 논리적 그룹(언어/카테고리 등) 기준으로
  나머지 shard에 균등 분배한다. 이때 그룹 기준이 실제로 균등한지(예: 그룹당
  같은 keyword 개수) 확인해야 한다 — 나중에 그룹 하나만 커지면 그 shard만
  한도를 넘을 수 있다.
- **프레임워크 기능이 관례를 벗어나는 부분은 실제 배포로 직접 확인**한다.
  예: 일부 프레임워크는 sitemap을 여러 파일로 나누면 상위 진입점(`/sitemap.xml`)
  을 자동으로 만들어주지 않는다 — "될 것"이라고 가정하지 말고 실제 배포 후
  URL에 접근해 상태 코드를 확인한다. 문제가 있으면 표준 포맷(`<sitemapindex>`)을
  직접 만들어 기존에 검색엔진에 등록됐을 URL이 계속 유효하도록 안전장치를 둔다.
- robots.txt에는 실제로 존재하는 모든 sitemap shard URL을 전부 나열한다
  (sitemap 프로토콜은 `Sitemap:` 줄을 여러 개 허용한다).

## 5. 대규모 Local SEO(또는 대규모 조합형 페이지) 설계 시 주의점

수만~수십만 개 규모의 조합형 페이지(지역×키워드, 카테고리×속성 등)를 설계할 때
공통으로 적용 가능한 원칙:

### Whitelist를 유일한 진실로
- "이론상 가능한 조합 전부"와 "실제로 공개하는 조합"을 반드시 분리한다.
- 공개 대상은 하나의 명시적 whitelist 계산 함수(예: 지역 마스터 데이터 ×
  선정된 키워드 목록의 cross product)로만 정의하고, **sitemap / 페이지 렌더링 /
  검증 스크립트가 전부 이 함수 하나를 공유**하게 만든다. 같은 목록을 여러 곳에
  따로 정의하면 반드시 어긋난다.
- 렌더링 함수 안에서 whitelist 검사를 다시 하고, 통과 못 하면 404 처리한다.
  URL 라우팅 레벨의 "그럴듯해 보이는 조합"이 전부 실제로 열리게 두지 않는다.

### On-Demand ISR로 빌드 비용 관리
- 조합 수가 수만 개를 넘으면 전부를 빌드 시점에 SSG하지 않는다. 대표 샘플
  (스모크 테스트용 1개 그룹)만 빌드 시점에 만들고, 나머지는
  `dynamicParams = true` + 적절한 `revalidate` 주기로 **최초 요청 시 생성 후
  캐시**되게 한다.
- revalidate 주기는 "콘텐츠가 실제로 바뀌는 빈도"에 맞춘다. 결정적 함수로
  생성되는 콘텐츠(같은 입력 → 항상 같은 출력)라면 재배포 시점에만 내용이
  바뀌므로, 하루~일주일 단위의 긴 주기로도 충분하다.

### Deterministic Content Generator
- 조합마다 사람이 손으로 문구를 쓰는 것은 수만 개 규모에서 불가능하고 품질도
  들쭉날쭉해진다. 대신 **"입력(지역/카테고리 등) → 출력(제목/H1/본문/FAQ/메타)"을
  순수 함수로 만든다.**
- 재료(문구 조각, 카테고리별 세부 프로필)와 조립 로직을 분리한다 — 재료 파일은
  값만 담고, 조립 로직은 별도 엔진 파일에 둔다. 그래야 재료를 늘려도 로직을
  건드리지 않고, 로직을 바꿔도 재료 파일을 뒤지지 않아도 된다.
- 특정 세부 카테고리에만 있는 값(예: 특정 시험에만 있는 세부 정보)은 "없으면
  공용 fallback 문구를 쓰는" 구조로 만들어, 데이터가 없다고 페이지가 깨지거나
  빈 문구가 나가지 않게 한다.

## 6. 페이지 유사도 개선 원칙 / Thin·Doorway Page 위험 방지

대량 생성 페이지의 가장 큰 리스크는 "지역명/카테고리명만 바뀐 사실상 동일한
페이지"로 검색엔진에 doorway page로 판정되는 것이다.

- 템플릿에 변수만 꽂아 넣는 구조를 피하고, **의도(intent) 축을 추가로 둔다**
  (예: 같은 카테고리라도 "가격 문의형/비교형/입문형" 등 실제 검색 의도가 다른
  변형을 여러 개 준비해 지역/카테고리에 따라 다른 조합이 나가게 한다).
- 페이지마다 달라야 하는 최소 요소: title, meta description, H1, 도입부 문장,
  추천 대상 문구. 이 요소들이 전부 같은 문자열 템플릿에 변수 하나만 바뀌는
  구조라면 위험 신호다.
- **검증 스크립트로 실제 중복을 기계적으로 확인**한다 — 공개 대상 전체 조합을
  순회하며 title/description/H1 문자열 중복 여부를 체크하는 스크립트를 만들어
  둔다. 사람이 수만 개를 눈으로 검토하는 것은 불가능하다.
- 오프라인 실체가 없는 서비스(온라인 전용)라면, "OO 지점/센터/방문" 같은
  존재하지 않는 오프라인 표현이 템플릿에서 새 나가지 않는지 금칙어 목록으로
  기계적으로 검사한다.
- 지역/카테고리 데이터가 확장될 때 동명이인(같은 이름의 지역이 여러 상위
  행정구역에 존재하는 경우)이 생길 수 있다 — 본문에 노출되는 이름은 상위
  구분자를 포함해 전국적으로 유일하게 만들되, URL 자체는 원래 표기를 유지해
  기존에 색인된 링크를 깨지 않는다.

## 7. 내부링크 / 지역 허브(대규모 콘텐츠 브라우징 계층) 설계

- 대량 생성 리프 페이지(검색엔진/직접 URL 진입용)와 **사람이 클릭해서 탐색하는
  브라우징 허브는 서로 다른 목적의 별개 계층**으로 설계할 수 있다. 리프
  페이지는 검색 유입, 허브는 내부 탐색·크롤링 유도 역할을 분리해서 맡긴다.
- 허브 계층(상위 카테고리 → 하위 카테고리 → 리프)은 **깊이가 얕은 상위
  레벨(전체/상위 카테고리)은 빌드 시점에 전부 생성**해도 비용이 작지만,
  최하위 레벨(개수가 수천~수만 개)은 리프 페이지와 동일하게 대표 샘플만 미리
  만들고 나머지는 on-demand로 생성한다.
- 검색용 인덱스(예: 지역/카테고리 이름 전체 목록)를 클라이언트에 그대로
  번들링하면 초기 로딩이 무거워진다 — **사용자가 실제로 검색 UI를 사용할
  때(포커스 시)만 별도 경량 API로 지연 로드**하고, 그 응답 자체도 정적
  캐시(예: `force-static` + 긴 max-age)로 만들어 서버 비용을 줄인다.
- 리프 페이지에서 나가는 내부 링크("가지치기")는 **개수를 의도적으로 제한
  한다**(예: 5~10개 수준). 화이트리스트 전체 조합에 대해 링크를 수십~수백 개씩
  붙이면 페이지가 링크 팜처럼 보이고 실제 사용자 경험도 나빠진다. 우선순위:
  같은 그룹의 다른 변형(1~2개) → 관련 핵심 페이지 → 관련 콘텐츠(매거진/블로그) →
  다른 상위 카테고리 → 사이트 전역 유틸리티(진단 도구 등).
- sitemap에는 **리프 페이지 전체 + 허브의 상위 레벨(전체/1단계)만** 포함하고,
  허브의 중간~최하위 레벨은 sitemap에 넣지 않고 실제 `<a>` 링크로만 크롤링을
  유도해도 된다 — sitemap을 가볍게 유지하면서도 크롤러가 실제 링크를 타고
  들어갈 수 있다면 문제가 없다.

## 8. Breadcrumb 설계

- 화면에 보이는 Breadcrumb 배열과 JSON-LD BreadcrumbList는 **같은 배열을
  그대로 재사용**해서 둘이 어긋나지 않게 한다.
- Breadcrumb 단계 수는 실제 URL 구조(세그먼트 개수)와 일치시킨다. URL이
  4단계인데 Breadcrumb이 2단계만 보여주면(중간 단계 생략) 사용자와 검색엔진
  모두에게 실제 계층 구조를 잘못 전달한다.
- 상위 계층에 해당하는 허브 페이지가 실제로 존재한다면 각 Breadcrumb crumb에
  그 페이지로의 링크를 건다 — 존재하지 않는 페이지로 링크하지 않는다(리프
  페이지가 whitelist를 통과했다면 그 상위 허브도 항상 존재한다는 것을 설계
  단계에서 보장해둔다).

## 9. Magazine / Content Hub 설계

- 콘텐츠 허브(블로그/매거진)는 **화이트리스트 방식**으로 관리한다 — 존재하는
  글의 slug 목록을 명시적으로 만들고, 그 목록에 없는 slug는 빌드 시점부터
  404로 고정한다(동적으로 아무 slug나 렌더링되지 않게).
- 글 데이터는 언어/카테고리별 파일로 나누고 index 파일에서 합쳐서 export —
  한 파일이 무한정 커지는 것을 방지하고, 언어별 담당자가 각자 파일만 보고
  작업할 수 있게 한다.
- 글 간 관련 콘텐츠 연결(관련 글 slug 배열)은 **존재하지 않는 slug(오타 등)를
  조용히 걸러내는 조회 함수**를 통해서만 노출한다 — 깨진 링크가 화면에 그대로
  나가지 않게 한다.
- 카드형 목록 UI를 여러 페이지(허브/사이드바/관련 콘텐츠)에서 재사용할 때는
  같은 카드가 시각적으로 반복되어 지루해 보이지 않도록 페이지별로 카드 밀도나
  레이아웃에 변화를 준다 — 실제로 "반복되는 UI 패턴" 자체가 나중에 별도
  리팩터링 대상이 될 수 있다는 것을 초기에 인지한다.

## 10. 후기(리뷰) 페이지 설계

- **후기 데이터에 출처 타입 필드를 반드시 둔다**(예: "실제 확인된 사례" vs
  "아직 검증되지 않은 프로토타입/더미"). 이 필드로 실제 화면에 노출할 데이터를
  걸러내는 함수를 하나만 만들고, production 화면은 반드시 그 함수만 사용한다.
- 프로토타입/더미 데이터는 **삭제하지 말고 명시적으로 미노출 처리**한다 —
  나중에 실제 데이터로 교체할 자리 표시자 역할을 하면서도, 실수로 화면에
  나가는 사고를 코드 레벨에서 막는다.
- 원문 출처가 있는 사례는 원문을 그대로 복사하지 않고 사실만 재구성
  (paraphrase)한다. 원문에 없는 나이/점수/기간 등 구체적 수치를 임의로
  추가하지 않는다. 실명 노출 권한이 없다면 역할/구분만 남기고 이름은
  노출하지 않는다.
- 언어/카테고리별로 실제 확보된 후기 수가 크게 불균형할 수 있다 — 실제 개수를
  조작하지 않고, **노출 순서만 라운드로빈 등으로 섞어서** 특정 카테고리가
  목록 전체를 뒤덮지 않게 한다.
- 지역별 페이지에서 "OO동 거주자 후기"처럼 후기 작성자의 실제 거주지를
  추측해서 서술하지 않는다 — 확인되지 않은 사실을 만들어내는 것과 같다.

## 11. 첫 5초 UX 점검 방법

새 페이지(특히 랜딩/히어로)를 완성한 뒤 아래를 스스로 점검한다:

1. 화면을 캡처하거나 실제로 열어서 **5초만 보고** "무슨 서비스인지 / 누구를
   위한 것인지 / 핵심 행동(CTA)이 무엇인지"가 설명 없이 이해되는지 확인한다.
2. Hero 영역에 텍스트를 몰아넣지 않는다 — 헤드라인 1개 + 보조문구 1개 +
   CTA 1~2개 정도로 제한하고, 나머지 정보는 스크롤 아래 섹션으로 내린다.
3. 이해에 실패했다면 원인을 "정보가 부족해서"가 아니라 "정보가 너무 많아서"
   인 경우부터 의심한다 — 실전에서는 후자가 훨씬 흔하다.
4. 브랜드/카피가 화려해도 위 3가지(서비스/대상/행동)가 5초 안에 안 잡히면
   실패로 간주하고 우선순위를 다시 정리한다.

## 12. "AI티" 나는 디자인 패턴과 개선법

일반적으로 AI가 초안으로 만든 디자인에서 반복적으로 나타나는 패턴과 대응:

| AI티 나는 패턴 | 개선 방향 |
|---|---|
| 카드가 남발되고 모든 콘텐츠를 카드로 감쌈 | 실제로 비교/선택이 필요한 콘텐츠만 카드로, 나머지는 단순 리스트/텍스트 블록 |
| 과한 그라디언트, 큰 bounce/zoom 애니메이션 | 절제된 opacity/translateY 정도의 짧은 진입 모션만 유지 |
| 모든 요소가 동시에 움직임 | 스크롤 시 순차적으로(delay 부여) 절제되게 등장 |
| 페이지마다 다른 디자인 언어(카드 스타일/버튼 스타일이 페이지마다 다름) | 공용 디자인 토큰(색상/radius/spacing)을 먼저 정의하고 전 페이지가 공유 |
| 지나치게 균일한 3열 그리드로 모든 정보를 나열 | 정보 위계에 따라 레이아웃 비중을 다르게(중요한 것은 크게, 부가정보는 작게) |
| 이모지/아이콘 남발로 장식 | 의미 있는 곳에만 최소한으로 사용 |
| 빈 상태(opacity 0)가 오래 유지되는 스크롤 reveal | 진입 애니메이션은 빠르게 끝나되 너무 휙 지나가지 않을 정도로 튜닝 |

원칙은 "화려함"이 아니라 **일관성 + 절제 + 정보 위계**다. 사용자가 움직임을
줄이길 원하면(`prefers-reduced-motion`) 애니메이션/트랜지션을 즉시 처리로
전환하는 전역 규칙을 두고, 이를 개별 컴포넌트에서 우회하지 않는다.

## 13. 모바일 Overflow 점검법

- 좁은 화면(390px 기준)에서 가로 스크롤이 생기는 가장 흔한 원인: 고정 너비
  요소, `padding`이 아닌 `margin`으로 좌우 여백을 준 컨테이너, 긴 문자열이
  줄바꿈 없이 흐르는 텍스트, 그리드/flex의 `min-width` 미설정.
- 점검 순서: (1) 390px로 리사이즈 (2) 페이지 전체를 스크린샷이 아니라 **실제
  DOM 텍스트/레이아웃을 읽어서** 확인 (3) 가로 스크롤바가 생기는지 확인
  (4) 생긴다면 어떤 요소가 뷰포트 폭을 넘는지 하나씩 좁혀가며 찾는다.
- 표/다이어그램/코드블록처럼 원래 넓어야 하는 콘텐츠만 개별
  `overflow-x: auto` 컨테이너로 감싸고, 페이지 본문 자체는 가로 스크롤이
  생기지 않게 한다.
- 이미지에는 `max-width: 100%`를 기본으로 두고, `aspect-ratio` 박스에는
  화면보다 넓은 `min-width`를 주지 않는다.

## 14. 390 / 768 / 1440 Playwright(브라우저 자동화) QA

- 커밋된 자동 테스트 스위트가 없어도, **에이전트 기반 브라우저 자동화로
  매 주요 변경마다 3개 뷰포트를 순회하는 수동 QA 루틴**을 정착시키는 것만으로
  충분히 효과가 있다: 390px(모바일) / 768px(태블릿) / 1440px(데스크톱).
- 스크린샷/스크롤 API 결과만으로 "정상"이라고 판단하지 않는다 — 스크린샷은
  실제 렌더링과 다르게 보일 수 있고 스크롤 API 값도 신뢰할 수 없는 경우가
  있다. **실제 페이지 텍스트 추출(get_page_text 등) + 네트워크/콘솔 로그**까지
  함께 확인해야 진짜 버그와 도구의 착시를 구분할 수 있다.
- 뷰포트마다 확인할 최소 체크리스트: 가로 스크롤 여부, Hero 텍스트 잘림 여부,
  버튼/폼 요소 터치 영역, sticky 헤더/nav 겹침, 이미지 크롭 위치.
- QA 과정에서 생성되는 임시 스냅샷/산출물 폴더는 `.gitignore`에 추가하거나
  최소한 커밋 전 `git status`로 매번 걸러낸다.

## 15. Validation 체계

- **작은 UI/CSS 수정**: 타입 체크(`tsc --noEmit`)만으로 충분.
- **Route/Metadata/데이터 엔진/아키텍처 변경**: 타입 체크 + 실제 프로덕션
  빌드(`next build` 등)까지 실행 — 개발 서버에서는 안 잡히는 문제(shard
  id 타입 불일치 등)가 실제 빌드에서만 드러나는 경우가 있다.
- **대량 생성 콘텐츠(SEO 등)는 전용 검증 스크립트를 별도로 만든다** — 공개
  대상 전체를 순회하며 제목/설명/H1 중복, canonical 형식, 금칙 표현 사용
  여부, 내부 링크 유효성(가리키는 페이지가 실제로 존재하는지)을 기계적으로
  검사한다. 수만 개 규모에서는 사람이 눈으로 검수하는 것이 불가능하므로
  이 스크립트가 사실상 유일한 품질 게이트다.
- 여러 개의 작은 수정이 이어질 때는 매번 풀빌드를 돌리지 말고, **작업 배치가
  끝난 시점에 한 번만** 무거운 검증을 실행해 시간을 아낀다.
- 가능하면 "성공했다"고 결론 내리기 전에 실제로 확인 가능한 것(HTTP 상태
  코드, 렌더링된 HTML, sitemap/robots 응답, JSON-LD 파싱 결과, 404 여부)을
  직접 확인한다 — 코드가 논리적으로 맞아 보여도 실제 배포 환경(프레임워크
  버전, 플랫폼 특성)에서 다르게 동작하는 경우가 실제로 있었다(4번 항목의
  sitemap 사례 참고).

## 16. Git → Vercel(또는 동급 플랫폼) 배포 전 체크리스트

- 작업 시작 전 `git pull`로 원격 최신 상태를 받는다(여러 기기/환경을 오가며
  작업하는 경우 특히 중요).
- 커밋 전 `git status`로 의도하지 않은 미커밋 변경이 섞여 있지 않은지 반드시
  확인한다 — 특히 `git add -A`/`git add .`처럼 범위를 명시하지 않는 스테이징은
  피하고 대상 파일을 명시한다.
- 민감 정보(`.env*`, API 키, 토큰)는 `.gitignore`에 반드시 포함하고, 커밋
  대상에 우연히 섞이지 않았는지 diff로 확인한다. 파일명이 평범해 보여도
  내용에 비밀값이 있을 수 있으니 의심되면 내용을 확인한다.
- 검색엔진 소유권 인증 파일(`public/*.html` 등)은 인증 완료 후에도 삭제/수정/
  `.gitignore` 추가를 하지 않는다 — 삭제하면 소유권 인증이 풀릴 수 있다.
- 배포 플랫폼과 프로젝트를 연결하는 설정 파일(예: `.vercel/project.json`)은
  프로젝트 식별자를 담고 있어 유용하지만, 이 자체가 배포 권한을 주지는
  않는다 — 실제 배포/도메인 조회는 플랫폼 계정 인증(팀 스코프 포함)이
  별도로 필요하다는 것을 인지한다.

## 17. 이미지 라이선스 / 출처 관리

- 무료 라이선스 스톡 이미지를 쓰더라도 **출처 추적용 데이터 파일**(사진작가/
  원본 URL/라이선스 종류/용도)을 별도로 관리한다 — 저작자 표시 의무가 없는
  라이선스라도, 나중에 이미지를 교체하거나 라이선스를 재확인해야 할 때
  필요하다.
- 이미지 속 인물이 실제 서비스 관계자(강사/수강생/직원)가 아니라면, 그 사실을
  데이터 파일 주석에 명시하고 실제 인물 데이터(코치/후기 등)와 절대 연결하지
  않는다 — 혼동되면 "가짜 인물을 실제 인물처럼 노출"하는 심각한 신뢰 문제로
  이어진다.
- 이미지 교체 시 출처 파일의 관련 필드(출처/작가/프로필/라이선스/alt)를 함께
  갱신한다 — 이미지만 바꾸고 메타데이터를 갱신하지 않으면 출처 추적이
  끊긴다.
- 언어/문화권/목적이 있는 서비스라면 이미지의 맥락(인물 구성, 배경, 텍스트
  노출)이 실제 타겟과 어긋나지 않는지 항상 확인한다 — 배너 이미지를 나중에
  다시 보니 텍스트/맥락이 실제 카테고리와 안 맞아서 교체한 사례가 실제로
  있었다(문서 갱신 시점 기준 최근 실패 사례 13번 참고).

## 18. 실제 작업 중 발견했던 실패 사례와 예방책

- **프레임워크 기능의 암묵적 가정을 검증 없이 믿음**: sitemap을 여러 파일로
  나누는 기능을 쓰면 프레임워크가 상위 진입점을 자동으로 만들어 줄 것이라고
  가정했다가, 실제 배포에서 404가 나는 것을 발견했다. → 예방책: "문서에
  안 나온 동작"이나 "확신이 없는 프레임워크 동작"은 실제 배포 후 URL로
  직접 확인하고, 필요하면 표준 스펙에 맞는 대체 구현을 직접 만든다.
- **동적 라우트 파라미터의 런타임 타입 불일치**: 타입 선언은 숫자였지만
  실제 런타임 값이 문자열로 들어와, 값 비교(`===`)가 항상 실패해 특정
  분기(예: shard 0)가 빈 결과를 반환하는 버그가 있었다. → 예방책: 동적
  라우트 파라미터는 타입 선언을 그대로 믿지 말고, 비교 전에 명시적으로
  타입을 변환한다.
- **이미지-맥락 불일치가 배포 후에야 발견됨**: 특정 카테고리 배너에 그
  카테고리와 맥락이 약한(다른 문화권/상황처럼 보이는) 이미지가 쓰인 채로
  배포되었다가 나중에 교체되었다. → 예방책: 이미지를 넣을 때마다 "이
  이미지가 이 페이지의 언어/목적/대상과 실제로 맞는가"를 체크리스트로
  스스로 점검한다.
- **대량 생성 콘텐츠의 초기 버전이 템플릿 티가 남**: 조합형 페이지 초기
  버전이 지역명만 바뀌는 사실상 동일 문구였다가, intent(검색 의도) 축을
  추가해 고유성을 개선했다. → 예방책: 대량 생성 콘텐츠는 출시 전에 반드시
  "샘플 몇 개를 나란히 놓고 실제로 달라 보이는가"를 사람이 직접 비교
  검토한다.
- **Breadcrumb 깊이가 실제 URL 구조와 어긋남**: URL은 4단계인데 Breadcrumb이
  더 얕게 표시되던 버그가 있었다. → 예방책: Breadcrumb 배열을 URL 세그먼트
  구조에서 자동으로 도출하거나, 최소한 세그먼트 개수와 Breadcrumb 항목
  개수가 일치하는지 코드 리뷰에서 항상 확인한다.
- **반복되는 UI 카드 패턴이 여러 페이지에서 그대로 재사용되어 지루해짐**:
  같은 카드 컴포넌트를 허브/사이드바/관련 콘텐츠 영역에 그대로 반복
  사용하다가 나중에 계층 구조를 다듬었다. → 예방책: 같은 컴포넌트를 여러
  화면에 재사용할 때, 화면마다 실제로 밀도/레이아웃 변화를 줄 필요가
  없는지 미리 검토한다.

## 19. 최소 시간으로 높은 품질을 내기 위한 작업 순서

빠른 속도로 직접 운영하는 1인/소수 운영자에게 실제로 효과가 있었던 순서:

1. **먼저 실제로 동작하는 최소 버전을 만든다** — 핵심 전환 지점(문의/결제 등
   외부 연동 포함)까지 끝까지 연결된 얇은 버전을 가장 먼저 완성한다.
2. **Source of Truth 데이터 구조를 컴포넌트보다 먼저 굳힌다** — 이후 콘텐츠
   확장이 "새 데이터 추가"만으로 끝나도록 만든다.
3. **기술 SEO 뼈대(robots/sitemap/canonical/schema)를 콘텐츠가 적을 때
   먼저 세팅**한다.
4. **대량 생성이 필요한 영역은 whitelist + on-demand ISR + deterministic
   generator + 검증 스크립트 4종 세트를 한 번에 설계**한다 — 이 중 하나만
   빠지면(특히 검증 스크립트) 나중에 품질 문제를 사람이 수동으로 찾아야
   한다.
5. **큰 기능 단위가 끝날 때마다 타입체크 → (필요 시) 빌드 → 실제 URL/렌더링
   확인**까지 마치고 다음 작업으로 넘어간다. 작은 수정을 여러 개 이어갈
   때는 검증을 배치 끝에 한 번만 몰아서 한다.
6. **불필요한 재설계를 하지 않는다** — 이미 정상 동작하는 기능은 "더
   깔끔해 보인다"는 이유만으로 갈아엎지 않는다. 리팩터링은 명확한 문제가
   있을 때만 한다.
7. **문서(이 파일 같은 운영 기록)는 큰 작업이 끝난 시점에만 갱신**한다 —
   매 사소한 수정마다 문서를 고치면 그 자체가 시간 낭비가 되고, 반대로
   전혀 갱신하지 않으면 문서가 코드보다 오래된 정보를 담게 되어 신뢰할 수
   없어진다. 코드가 항상 최종 진실이라는 것을 문서 자체에도 명시해둔다.
